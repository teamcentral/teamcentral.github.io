central command backfill-default-grants ​

Give each Command user with no default grant one equal to today's route.

Today an approved-app (MCP) caller routes by User.CustomerId -> that customer's ClientId. For each user with no default grant whose customer exists and has a ClientId that parses as a GUID:

  • if one of their grants names that environment (ignoring case and GUID form), it is marked isDefault = true and otherwise left as it is;
  • otherwise one grant is added: { environmentId = ClientId (lower-case, hyphenated), customerId = customer id, isDefault = true, roleIds = [] }.

Never touched: users that already hold a default, including several (reported only). Every user holding grants is listed with its default state and today's route. The summary counts the users a header-less approved-app call would still refuse under Enforce once the plan is applied, and how many of them route today. Skipped and reported: every row sharing an email (case-insensitive, untrimmed, as the runtime matches), a missing or soft-deleted customer, and an empty or non-GUID ClientId. Users on a soft-deleted customer and duplicate-email groups are always listed, on a dry run too, and a user with both reasons is in both lists; duplicates are never resolved. Also always listed: customers tagged for their ClientId only in another case or GUID form, ClientIds more than one live customer claims, and, as a cleanup hint only, ClientIds a soft-deleted customer also claims (a deleted customer owns nothing, so these do not affect access). Customers with no environment tag for their ClientId (matched ignoring case and GUID form), and customers whose names differ only by a trailing environment word, are reported. None of these is ever written.

Output is ids only: no emails, names or secrets. Writes go one user at a time as a patch of the user's grants; each user is re-read and re-decided just before its write, a failure is reported without stopping the run, and the run ends with a fresh re-plan that should find zero writes. Re-running after --apply plans zero writes.

Connects as the current Azure credential (DefaultAzureCredential), hydrating the config's secrets from its own vault, as provision branding does.

Usage ​

central command backfill-default-grants [options]

Options ​

OptionDescriptionRequired
--config <FileInfo>Path to the platform config (customerconfigs AppSettings/centralconfig-{env}.json); its databaseId must be CentralCommandDatabase.Yes
--applyWrite the planned grants. Without it, nothing is written and the plan is printed.No

Examples ​

bash
# Dry run (the default): print the plan, write nothing
  central command backfill-default-grants --config ../customerconfigs/AppSettings/centralconfig-dev.json

  # Write the plan
  central command backfill-default-grants --config ../customerconfigs/AppSettings/centralconfig-dev.json --apply
